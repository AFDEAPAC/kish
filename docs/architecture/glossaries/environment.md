# Test Environment Domain Specification

## 1. Overview

Test Environment 描述一個 TestCase 執行測試時所處的環境狀態。

它是 TestCase 的必要組成部分，主要用來回答：

- 測試在哪裡執行？
- 執行時的系統狀態是什麼？
- 使用了哪些 OS / kernel / GPU / ROCm / Python / package？
- 測試是否在 container、physical host、VM 或其他環境中執行？
- 是否存在支撐該測試環境的外部環境？

---

## 2. Core Concept

Test Environment 由兩部分組成：

```text
TestEnvironment
├── execution_environment
└── supporting_environments[]
```

---

## 3. execution_environment

`execution_environment` 代表測試命令實際執行的環境。

它是必填欄位。

範例：

* container 內執行 benchmark
* physical server 上直接執行 benchmark
* VM 內執行 benchmark
* Kubernetes pod/container 內執行 benchmark

```text
execution_environment = where the test command was actually executed
```

---

## 4. supporting_environments

`supporting_environments` 代表支撐 execution environment 的外部環境。

它是選填欄位。

範例：

* container 的 physical host
* VM 的 physical host
* Kubernetes pod 所在 node
* Kubernetes node 背後的 physical host

```text
supporting_environment = external environment that hosts or supports the execution environment
```

---

## 5. Common Scenarios

### 5.1 Test Runs Inside Container

```text
TestEnvironment
├── execution_environment: container
└── supporting_environments:
    └── physical_host
```

---

### 5.2 Test Runs Directly on Physical Server

```text
TestEnvironment
├── execution_environment: host
└── supporting_environments: []
```

---

### 5.3 Test Runs Inside VM

```text
TestEnvironment
├── execution_environment: virtual_machine
└── supporting_environments:
    └── host
```

---

### 5.4 Test Runs Inside Kubernetes Pod

```text
TestEnvironment
├── execution_environment: container
└── supporting_environments:
    ├── kubernetes_node
    └── host
```

## 6. EnvironmentSnapshot

Each environment is represented as an `EnvironmentSnapshot`.

An `EnvironmentSnapshot` is an immutable JSON snapshot describing the environment where a test was executed or a related environment context. It is generated by a collector tool such as `kish detect`.

```text
EnvironmentSnapshot
├── schema_version
├── kish_version
├── scope
├── type
├── collected_at
├── data
├── package_sets[]
├── raw
└── collectors[]
```

The `id` field is assigned by the backend after upload and is not included in the local snapshot file produced by `kish detect`.

---

## 7. EnvironmentSnapshot Fields

### 7.1 schema_version

* type: string
* required: true

Example:

```text
environment-snapshot/v1
```

---

### 7.2 kish_version

* type: string
* required: true

The version of the `kish` CLI tool that produced this snapshot.

Example:

```text
0.1.0
```

---

### 7.3 scope

* type: string
* required: true

Describes the relationship of this environment snapshot to the test execution.

Allowed values:

```text
execution
context
```

Definitions:

```text
execution:
The environment where the test command actually runs.

context:
An additional environment that provides context for the testcase,
such as the host environment of a container.
```

`kish detect` always emits `scope = execution` in v1.

Note: earlier versions of this document used the field name `role` with values `execution`/`supporting`. This has been superseded by `scope` with values `execution`/`context`.

---

### 7.4 type

* type: string
* required: true

Describes the nature of the environment.

Allowed values:

```text
container
host
bare_metal
virtual_machine
unknown
```

Auto-detection rule used by `kish detect` v1:

```text
if /.dockerenv exists → type = container
else                  → type = host
```

`bare_metal`, `virtual_machine`, and `unknown` are reserved for future detection logic.

---

### 7.5 collected_at

* type: timestamp (RFC 3339 / ISO 8601)
* required: true

---

### 7.6 data

* type: map[string]string
* required: true

`data` stores normalized key-value environment facts.

Example keys:

```text
os.name
os.id
os.version
os.version_id
kernel.name
kernel.release
kernel.version
architecture
hostname
cpu.model
cpu.count
memory.total_bytes
gpu.vendor
gpu.models
gpu.count
gpu.ids
rocm.version
rocm.version_source
rocm.info_version_file.exists
rocm_smi.available
rocm_smi.runnable
rocm_smi.error
rocminfo.available
rocminfo.runnable
rocminfo.error
python.version
python.executable
python.prefix
python.virtualenv
container.detected
container.evidence
container.runtime
docker.image
docker.image_digest
```

Boolean-like values in `data` are serialized as strings: `"true"`, `"false"`, `"unknown"`.

Per-device GPU information is represented in the top-level `devices` field as structured data rather than as comma-separated strings in `data`.
Summary GPU facts (`gpu.count`, `gpu.vendor`) remain in `data` for quick querying.

---

### 7.7 package_sets

* type: PackageSet[]
* required: false

Package lists are stored separately from `data` because they can be large and have their own structure.

---

### 7.8 raw

* type: map[string]string
* required: false

`raw` stores command outputs or unstructured collector data for debugging and future re-parsing.

Example keys:

```text
/proc/1/cgroup
uname -a
cat /etc/os-release
```

Package command raw output (e.g. `dpkg -l`, `pip list`) is not included in the main snapshot JSON by default.
Structured package data under `package_sets[].packages` is preferred.
Raw package output may be supported later as external files or behind an explicit flag.

---

### 7.9 collectors

* type: CollectorReport[]
* required: false

Summary execution report for each collector that ran during detection. See `CollectorReport` section.

---

### 7.10 devices

* type: Devices
* required: false

Structured hardware device information collected during detection.

```text
Devices
└── gpus[]   GPUDevice[]
```

Per-device GPU information is stored here rather than as comma-separated strings in `data`.
See `Devices` and `GPUDevice` sections.

---

## 8. EnvironmentScope

`EnvironmentScope` describes the role of a snapshot relative to the test.

| Value       | Description                                                         |
|-------------|---------------------------------------------------------------------|
| `execution` | The environment where the test command actually ran.               |
| `context`   | An additional environment that provides context (e.g. host of a container). |

---

## 9. EnvironmentType

`EnvironmentType` describes the nature of the environment.

| Value            | Description                                               |
|------------------|-----------------------------------------------------------|
| `container`      | A container (Docker, OCI, etc.).                         |
| `host`           | A general host environment (not further classified).     |
| `bare_metal`     | A physical server with no hypervisor.                    |
| `virtual_machine`| A virtual machine (KVM, QEMU, VMware, etc.).             |
| `unknown`        | Cannot be determined.                                    |

Future possible values: `kubernetes_node`, `slurm_node`, `cloud_instance`, `wsl`.

## 10. PackageSet

```text
PackageSet
├── type
├── manager
├── source
├── raw_file
└── packages[]
```

## 11. PackageSet Fields

### 11.1 type

* type: string
* required: true

Allowed values:

```text
system
python
```

Future possible values: `conda`, `npm`, `rocm`, `cuda`, `spack`, `source_build`.

---

### 11.2 manager

* type: string
* required: true

Allowed values:

```text
dpkg
rpm
pip
unknown
```

---

### 11.3 source

* type: string
* required: false

Examples:

```text
dpkg -l
rpm -qa
python3 -m pip list --format=json
pip list --format=json
```

---

### 11.4 packages

* type: Package[]
* required: false

---

### 11.5 raw_file

* type: string
* required: false

Relative path to the raw command output file produced alongside the snapshot JSON.

Raw package command output is written to a separate text file rather than embedded in the JSON,
because package lists can be very large. The `raw_file` field records the filename for traceability.

Filename format:

```text
snapshot_<collector>_<timestamp>.txt
```

Timestamp format: `YYYYMMDDTHHMMSSz` (e.g. `20260429T120000Z`).

Examples:

```text
snapshot_dpkglist_20260429T120000Z.txt
snapshot_rpmlist_20260429T120000Z.txt
snapshot_piplist_20260429T120000Z.txt
```

The file is written to the same directory as the snapshot JSON.
Structured package data in `packages[]` is the canonical output for querying.

## 13. Package Fields

### 13.1 name

* type: string
* required: true when parsed

---

### 13.2 version

* type: string
* required: false

---

### 13.3 architecture

* type: string
* required: false

Used mainly by system package managers.

---

### 13.4 release

* type: string
* required: false

Used mainly by RPM-based package managers.

---

### 13.5 location

* type: string
* required: false

The local filesystem path of a package when it is installed as an editable or local package.
Applies to Python packages only.

Example:

```json

  "name": "vllm",
  "version": "0.8.0",
  "location": "/workspace/vllm"
}
```

Populated from `editable_project_location` or `location` fields returned by
`pip list --format=json --editable`. Both field names are normalized to `location`.

## 14. Devices

`Devices` holds structured hardware device information collected during detection.

```text
Devices
└── gpus[]   GPUDevice[]
```

---

## 14.1 GPUDevice

`GPUDevice` represents a single detected GPU.

```text
GPUDevice
├── index
├── model
├── vendor
└── id
```

| Field    | Type   | Required | Description                                           |
|----------|--------|----------|-------------------------------------------------------|
| `index`  | int    | true     | Stable index within the detected output (0-based).   |
| `model`  | string | false    | GPU model name (e.g. "AMD Instinct MI300X").          |
| `vendor` | string | false    | GPU vendor (e.g. "AMD", "NVIDIA").                    |
| `id`     | string | false    | PCI bus ID (e.g. "0000:03:00.0"). Omitted if unknown.|

Example:

```json
{
  "devices": {
    "gpus": [
      {
        "index": 0,
        "model": "AMD Instinct MI300X",
        "vendor": "AMD",
        "id": "0000:03:00.0"
      },
      {
        "index": 1,
        "model": "AMD Instinct MI300X",
        "vendor": "AMD",
        "id": "0000:04:00.0"
      }
    ]
  }
}
```

`gpu.count` and `gpu.vendor` summary fields remain in `data` for quick filtering.
The `gpu.models` comma-separated string is not used; structured `devices.gpus` is the canonical representation.

## 16. Collector

A `Collector` is a plugin-like component responsible for collecting one category of environment data.

Each collector:
- Has a unique name
- Accepts a context (for timeout/cancellation)
- Returns a `CollectorResult`
- Must never terminate the whole detection process on failure
- Converts internal errors into `CollectorResult.Status = failed` or `partial`

v1 collectors (in execution order):

```text
1. linux_system   — OS, kernel, architecture, hostname
2. container      — container detection (/.dockerenv)
3. system_packages — dpkg or rpm package list
4. rocm           — ROCm version and runtime availability
5. gpu            — GPU detection (rocm-smi or lspci)
6. python_packages — Python version and pip packages
```

---

## 17. CollectorStatus

`CollectorStatus` describes the outcome of a collector run.

| Value     | Description                                                         |
|-----------|---------------------------------------------------------------------|
| `success` | Collector completed successfully.                                  |
| `partial` | Collector collected some data but one or more sub-steps failed.    |
| `skipped` | Collector is not applicable (e.g. required command is missing).    |
| `failed`  | Collector failed; detection process continues regardless.          |

---

## 18. CollectorResult

`CollectorResult` is the internal result returned by each collector to the detection service. It is not serialized directly into the output JSON.

```text
CollectorResult
├── name
├── status
├── started_at
├── finished_at
├── data
├── package_sets[]
├── devices        (optional structured hardware data, e.g. GPUDevice list)
├── raw
├── warnings[]
└── error
```

---

## 19. CollectorReport

`CollectorReport` is the summary of a collector's execution that appears in the top-level `collectors` field of the output snapshot.

Raw outputs and full data are not included in the report; they are merged into the snapshot's top-level fields.

```text
CollectorReport
├── name
├── status
├── warnings[]    (omitted if empty)
└── error         (omitted if empty)
```

## 20. Constraints

* Every TestCase must have exactly one `execution_environment`.
* `supporting_environments` may be empty.
* Environment snapshot must be generated by a collector tool such as `kish detect`.
* Environment snapshot should be treated as immutable after upload.
* Package lists should be stored under `package_sets`, not flattened into `data`.
* `data` should contain normalized, query-friendly key-value facts.
* Boolean-like values in `data` must be serialized as strings (`"true"`, `"false"`, `"unknown"`).
* `raw` should contain original command outputs for debugging and future re-parsing.
* Package command raw output is written to a separate file; `PackageSet.raw_file` records the filename.
* Individual package items must not contain a `raw` field; raw data belongs at `PackageSet.raw_file` only.
* Collector should not assume the environment is always a container.
* Collector should support direct physical host execution.
* A single collector failure must not fail the whole detection process.

---

## 21. Non-Goals

Test Environment does not define:

* parser behavior
* visualization behavior
* benchmark-specific result schema
* campaign grouping
* user permission model
* job execution model
